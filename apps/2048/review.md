# 2048 게임 앱 — Review 결과

Build 에이전트와 별개의 세션에서 `spec.md` / `index.html` / `style.css` /
`script.js`를 편견 없이 재검토했다. 이 세션에서는 `claude-in-chrome` 브라우저
확장이 연결되지 않아(재시도해도 "Browser extension is not connected" 오류)
지침이 요구한 실제 브라우저 조작(방향키/스와이프 입력, 다크모드 토글 클릭,
375px 리사이즈 스크린샷, 콘솔 로그 확인)을 직접 수행하지 못했다. 이 사실을
숨기지 않고 아래에 그대로 밝히며, 대신 (1) 정적 코드 검토와 (2) Node.js로
최소 DOM 스텁을 만들어 `script.js`를 실제로 실행시키는 방식으로 게임 로직을
엔드투엔드에 가깝게 검증했다. 브라우저 확장이 복구되면 4번(브라우저 실동작)
항목을 재확인할 것을 권장한다.

## 1. 코드 검토

| 항목 | 결과 |
|---|---|
| 밀기/병합 알고리즘 (좌회전 통일 방식, 4방향 회전/전치) | 통과 |
| 병합 "한 턴 1회" 규칙 (`2 2 2 2 → 4 4`, `8`이 아님) | 통과 |
| 새 타일 90/10 확률 | 통과 (실측 시뮬레이션 결과 하단 참고) |
| 이동 후 보드 불변이면 새 타일 미생성 | 통과 |
| 점수 계산 (병합 결과값 누적, best 갱신 시 즉시 저장) | 통과 |
| 패배 조건 (빈칸 없음 + 인접 동일값 없음) | 통과 |
| 승리 조건 (2048 최초 등장, 배너는 1회만, "계속하기"/"새 게임") | 통과 — 승리와 동시에 게임오버가 되는 엣지 케이스까지 이미 처리되어 있음 (계속하기 클릭 직후 `gameOver`면 바로 게임오버 오버레이 표시) |
| 프레임워크/외부 런타임 의존성 없음 | 통과 — `grep`으로 `http(s)://`, cdn, import/require 등 검색 결과 0건. `apps/2048/`에는 `index.html`/`style.css`/`script.js`/`spec.md` 4개 파일만 존재, 추가 자산 없음 |
| 다크모드 토큰 재정의 관례 (FOUC 방지 인라인 스크립트, `data-theme` 3상태) | 통과 — `index.html` head의 인라인 스크립트가 CSS 로드 전에 저장된 값이 `light`/`dark`일 때만 속성을 지정하고, 시스템 따름(값 없음)은 CSS의 `prefers-color-scheme` 쿼리에 맡기는 방식이 블로그 `theme.js` 패턴과 동일 |
| 명백한 버그/엣지 케이스 누락 | 발견하지 못함 (아래 시뮬레이션 테스트로 교차 검증) |

세부적으로 좌회전 합성 로직(`transpose`/`reverseRows`를 적용한 순서의 역순으로
되돌리는 방식)과 병합 마커(`mergedMarker`)의 좌표 역변환도 직접 손으로
추적해 검증했으며 오류 없음.

## 2. Node.js DOM 스텁을 통한 로직 실행 검증

브라우저 확장 없이도 실제 코드 경로를 실행해 검증하기 위해, `document`/
`localStorage`를 흉내 낸 최소 스텁을 만들어 `script.js`를 Node의 `vm` 모듈로
그대로 실행시키고 33개 항목을 자동 검사했다 (스크립트:
`dom-stub-test.js`, 세션 스크래치패드에 보관, 저장소에는 커밋하지 않음).
전부 통과:

- 좌/우/상/하 각 방향 밀기·병합 결과가 기대값과 일치.
- 병합 중복 방지 (`4 2 2 4 → 4 4 4`, 8이 아님).
- 변화 없는 이동은 턴을 소모하지 않음(새 타일 미생성) — 확인.
- 2000회 반복 스폰 시뮬레이션에서 "4" 비율이 약 9.8~11.2% (기대 10% 근접) — 확인.
- `isGameOver()`: 체커보드 풀보드에서 true, 인접 동일값이 하나라도 있으면 false — 확인.
- 2048 타일 최초 생성 시 승리 오버레이 표시, 메시지/버튼 2개(계속하기·새 게임) 정상 — 확인.
- **실제 랜덤 플레이를 게임오버가 날 때까지 반복 실행**(최대 20,000턴)해 자연스러운
  게임오버 도달까지 확인 — 보드가 가득 찬 상태에서 `isGameOver()`가 독립적으로도
  true에 동의, 게임오버 오버레이 표시, 메시지에 "게임 오버" 포함, 버튼 1개(새 게임),
  이후 입력이 `move()`에서 완전히 무시됨(보드 불변) — 모두 확인.
- "다시 시작": 점수 0, `gameOver`/`won` 초기화, `best`는 유지, 오버레이 닫힘, 타일
  2개 재생성 — 확인.
- 최고 점수: 갱신 즉시 `localStorage['2048-best-score']`에 저장되고, 새 스크립트
  인스턴스(새로고침 시뮬레이션)에서 `init()`이 동일 값을 다시 불러옴 — 확인.
- 테마 토글: 시스템→다크→라이트→시스템 3단 순환, 매 클릭마다 `data-theme` 속성과
  `localStorage['2048-theme']`가 함께 갱신됨 — 확인.

이 방식은 실제 렌더링/CSS/터치 이벤트/시각적 FOUC까지는 검증하지 못하는
한계가 있다 (아래 3번 참고).

## 3. 브라우저에서 직접 확인하지 못한 항목 (한계)

`claude-in-chrome` 확장이 연결되지 않아 아래 항목은 **실제로 확인하지 못했다.**
정적 분석으로 문제 없어 보인다고 판단한 근거만 남기며, 실제 확인을 대체하지
않는다:

- `file:///.../apps/2048/index.html`을 프로토콜 그대로 열었을 때의 동작 —
  코드상 `<script src="script.js">`, `<link rel="stylesheet" href="style.css">`
  모두 상대경로이고 `fetch`/모듈 임포트가 없어 file:// 프로토콜에서 막힐
  이유는 없어 보이나, 실제 로드 여부는 미확인.
- 콘솔 에러 유무(브라우저 고유 API 차이, 파싱 에러 등) — 미확인.
- 키보드 방향키 실입력 시 화면 상 타일 이동/애니메이션 — Node 스텁으로 상태
  전이는 검증했으나 실제 시각적 렌더링은 미확인.
- 터치 스와이프 제스처 실동작 — 이벤트 리스너 등록과 판정 임계값(24px)만
  코드로 확인, 실기기/에뮬레이터 터치는 미확인.
- 다크모드 토글 버튼 클릭 시 실제 테마 전환 및 새로고침 후 FOUC(흰 화면
  번쩍임) 유무 — 로직(속성/저장값)은 스텁으로 확인했으나 시각적 FOUC 여부는
  미확인.
- 375×667 뷰포트에서의 실제 레이아웃 — CSS를 손으로 계산하면 (`main` 최대
  30rem에 좌우 padding 1rem, `board-wrap` max-width 26rem에 width 100%,
  고정 px는 44px 터치 타깃과 border-radius류뿐) 343px 콘텐츠 폭 안에 보드와
  점수판·토글이 들어가 가로 스크롤이 발생할 이유가 안 보이지만, 실측은
  미확인.
- 타일 색상의 실제 렌더링 대비 — 라이트/다크 각 타일 배경-글자색 조합에
  대해 WCAG 상대휘도 공식으로 손계산했고 확인한 값(예: 다크 tile-8 대비
  약 4.63:1, 다른 값들은 대부분 5:1 이상)은 모두 4.5:1을 넘었으나, 브라우저
  렌더링/서브픽셀 안티앨리어싱 등 실측 차이는 반영하지 못함.

## 4. 수정 사항

코드 검토와 로직 시뮬레이션에서 **버그를 발견하지 못했다.** 따라서
`index.html` / `style.css` / `script.js`에 대한 수정은 하지 않았다.

## 5. 결론

- 게임 로직(밀기/병합/스폰 확률/점수/승리/패배)은 spec.md와 정확히 일치하며,
  Node 스텁을 통한 실행 검증(랜덤 플레이로 실제 게임오버 도달 포함)까지
  통과했다.
- 외부 의존성/CDN/프레임워크 없음, 다크모드 FOUC 방지 및 3상태 패턴도
  블로그 관례를 그대로 따른다.
- 다만 이번 세션은 브라우저 확장 연결 실패로 **실제 브라우저 시각적 확인
  (FOUC, 375px 실측 레이아웃, 실제 키보드/터치 조작 화면, 콘솔 에러)을
  수행하지 못했다.** 이 부분은 지침이 요구한 검증 항목 중 완료하지 못한
  부분이므로, 블로그에 카드를 추가해 임베드하기 **전에** 브라우저 확장을
  재연결한 뒤 최소한 아래를 한 번은 직접 열어 확인할 것을 권장한다:
  1. `file://` 프로토콜로 열리는지, 콘솔 에러가 없는지
  2. 375px 폭에서 가로 스크롤 없는지
  3. 다크 모드 새로고침 시 흰 화면 번쩍임(FOUC)이 없는지

  코드 자체의 논리적 정확성에는 이 세션 기준으로 문제를 찾지 못했으므로,
  위 3가지 시각적 확인만 통과하면 임베드해도 안전하다고 판단한다.
