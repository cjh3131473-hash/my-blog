# 픽셀 아트 에디터 — 설계 문서 (Plan)

## 개요

16×16 격자 위에 도트를 찍어 픽셀 아트를 그리고, 완성한 그림을 PNG 파일로
내려받는 에디터다. 색상 팔레트에서 색을 고르고, 클릭·드래그(마우스)와
터치 드래그(모바일)로 칸을 칠한다. 지우개로 칸을 비우면 그 칸은 저장할 때
투명하게 남는다. 핵심 기능은 **16×16 격자 드로잉 / PNG 저장 / 색상 팔레트**
세 가지이며, 나머지는 이 셋을 방해하지 않는 선에서만 넣었다.

`apps/pixel-art/` 안에서 완전히 자체 완결된다. 블로그 빌드 파이프라인
(`src/`, `posts/`, `dist/`, `site.config.js`)을 참조하지도 수정하지도 않으며,
정적 파일 그대로 열거나 서빙해서 동작한다. 프레임워크·런타임 라이브러리
없이 순수 HTML/CSS/바닐라 JS만 쓰고, 외부 도메인 요청은 0건이다.

설계의 우선순위는 "그리는 손맛"보다 **정확성과 접근성**에 둔다. 도트 하나를
정확히 찍는 것, 모바일에서 드래그하는 동안 페이지가 밀리지 않는 것,
키보드만으로도 그림을 그릴 수 있는 것이 화려한 도구 세트보다 먼저다.

## 파일 구조

```
apps/pixel-art/
  index.html   # 문서 구조: 헤더(제목 + 테마 토글), 16×16 격자, 도구줄, 팔레트, 안내 문구
  style.css    # 전체 스타일 — 색 토큰, 격자 레이아웃, 팔레트, 다크모드, 반응형
  script.js    # 드로잉 로직 — 픽셀 상태, 포인터/키보드 입력, 팔레트 선택, PNG 내보내기
  spec.md      # 이 문서 (Plan 산출물)
  review.md    # Review 단계 산출물
```

세 파일(`index.html`, `style.css`, `script.js`) 외에 이미지·폰트 등 추가 자산은
두지 않는다. 아이콘이 필요하면 텍스트나 순수 CSS로 해결한다. FOUC 방지용
테마 스크립트만 `index.html`의 `<head>` 안에 인라인으로 둔다(블로그와 같은 규칙).

## 캔버스/격자 설계

### DOM 격자 256개 vs `<canvas>` 하나 — DOM을 택한다

두 방식을 항목별로 비교했다.

| 항목 | DOM 256칸 | `<canvas>` 하나 |
|---|---|---|
| 입력 처리 | 이벤트 타깃이 곧 칸. 좌표 변환 불필요 | `getBoundingClientRect()` + 나눗셈으로 매번 좌표 변환 |
| 드래그 그리기 | 마우스는 자연스러움. 터치는 `elementFromPoint` 필요 | 마우스·터치 모두 좌표 변환 한 경로로 동일 |
| PNG 추출 | 오프스크린 캔버스를 새로 만들어 그려야 함 | 화면 캔버스에서 바로 뽑을 수 있음(단, 확대 배율 문제 있음) |
| 접근성 | 칸마다 실제 포커스 가능한 요소. 스크린리더가 위치·색을 읽음 | 캔버스 내부는 접근성 트리에 없음. 키보드 드로잉을 처음부터 직접 만들어야 함 |
| 성능 | 노드 256개 — 현대 브라우저에서 무시할 수준 | 더 가볍지만 이 규모에서는 차이가 체감되지 않음 |
| 스타일링 | 격자선·선택 하이라이트·체커보드를 CSS 토큰으로 처리 | 모두 JS 그리기 코드로 처리(다크모드 토큰 재사용이 어려움) |

**결론: DOM 격자(256칸)를 쓴다.** 근거는 세 가지다.

1. **PNG 추출에서 canvas가 얻는 이점이 실제로는 없다.** 어느 방식이든
   "픽셀 데이터 → 16×16 캔버스"를 다시 그려야 한다. 화면 캔버스는 확대된
   크기(예: 384px)이고 저장은 정수배 확대본이어야 하므로, 화면 캔버스를
   그대로 `toDataURL()` 하는 경로는 어차피 쓰지 않는다. 즉 canvas를 택해도
   오프스크린 캔버스는 따로 필요하다.
2. **접근성 차이가 결정적이다.** CLAUDE.md는 시맨틱 태그와 포커스 링 유지를
   요구한다. DOM 격자에서는 각 칸이 실제 포커스 가능한 요소라
   `aria-label="3행 5열, 빨강"` 같은 안내가 그대로 나가고, 방향키 이동과
   Enter/Space 칠하기가 자연스럽게 붙는다. canvas였다면 동일한 경험을 위해
   보이지 않는 대체 DOM을 따로 만들어야 하고, 그러면 결국 DOM 격자를 두 벌
   유지하는 셈이 된다.
3. **다크모드 토큰 체계가 유지된다.** 격자선·체커보드·선택 링을 CSS 변수로
   두면 `:root` 토큰 재정의만으로 다크모드가 끝난다. canvas였다면 이 색들을
   JS에서 `getComputedStyle`로 읽어와 다시 그려야 하고, 테마가 바뀔 때마다
   재렌더가 필요하다.

성능은 판단 근거에서 제외했다. 256칸은 두 방식 모두 문제가 되지 않는 규모다.
(격자 크기를 사용자가 바꾸는 기능은 비범위이므로 64×64 이상을 걱정할 필요도 없다.)

### 픽셀 데이터 자료구조

```js
// 길이 256의 1차원 배열. 값은 '#rrggbb' 문자열 또는 null(빈 칸).
const pixels = new Array(256).fill(null);

const index = row * 16 + col;   // 좌표 → 인덱스
const row = (index / 16) | 0;   // 인덱스 → 좌표
const col = index % 16;
```

- **1차원 배열**을 쓴다. 2차원 배열보다 순회·복사·인덱스 계산이 단순하고,
  DOM 칸 엘리먼트를 담는 배열(`cells[]`)과 인덱스를 1:1로 공유할 수 있다.
- **팔레트 인덱스(정수)가 아니라 색 문자열을 저장한다.** 커스텀 색상 입력을
  지원하기로 했으므로 팔레트에 없는 색이 들어올 수 있고, 인덱스로 저장하면
  "팔레트 밖 색" 처리를 위한 예외 경로가 하나 더 생긴다. 색 문자열은
  `ctx.fillStyle`과 `element.style.backgroundColor`에 그대로 넣을 수 있어
  변환 계층이 필요 없다. 256개 짧은 문자열이라 메모리도 문제되지 않는다.
- 빈 칸은 `null`이다. `'transparent'`나 `'#ffffff'`가 아니다 — 저장 시
  **투명**으로 남길 칸과 **흰색으로 칠한** 칸을 구분해야 하기 때문이다.
- 상태는 모듈 스코프 변수 몇 개로 충분하다: `pixels`, `currentColor`
  (`'#rrggbb'` 또는 `null`=지우개), `isDrawing`, `focusedIndex`.

### 화면 격자와 16×16 데이터의 관계

- 격자 컨테이너는 CSS Grid: `grid-template-columns: repeat(16, 1fr)`,
  `aspect-ratio: 1 / 1`, `width: min(100%, 30rem)`. 즉 **확대 배율은 고정값이
  아니라 화면 폭에 따라 유동적**이다. 375px 화면에서는 칸 하나가 약 21px,
  넓은 화면에서는 약 30px가 된다. 고정 픽셀 폭 금지 규칙을 지키기 위한 선택이다.
- 배율이 유동적이어도 **좌표 변환 코드는 없다.** 포인터 아래 엘리먼트에서
  `dataset.index`를 읽으면 끝이기 때문이다(아래 "드로잉 상호작용" 참고).
  이것이 DOM 격자를 택한 실질적 이득 중 하나다.
- `image-rendering: pixelated`는 **쓰지 않는다.** 이 속성은 작은 비트맵을
  확대해 보여줄 때 보간을 끄는 용도인데, DOM 격자는 이미지를 확대하는 것이
  아니라 각 칸이 배경색을 가진 독립 박스이므로 애초에 보간이 일어나지 않는다.
  동일한 효과가 필요한 곳은 저장용 오프스크린 캔버스뿐이며, 거기서는
  `ctx.imageSmoothingEnabled = false`로 처리한다.
- 칸 크기가 소수점으로 떨어져 격자선이 1px씩 어긋나 보일 수 있다. 격자선은
  각 칸의 `box-shadow: inset` 또는 컨테이너 `gap` + 배경색으로 그려
  서브픽셀 반올림의 영향을 최소화한다(구현 단계에서 둘 중 실제로 깨끗한
  쪽을 고른다).
- 빈 칸은 투명임을 알리기 위해 CSS 체커보드(`repeating-conic-gradient`)를
  칸 배경으로 깐다. 색이 칠해지면 그 위를 불투명 배경색이 덮는다.

## 드로잉 상호작용

### 포인터 이벤트로 마우스·터치를 하나로 처리

`mousedown`/`touchstart`를 따로 다루지 않고 **Pointer Events**
(`pointerdown` / `pointermove` / `pointerup` / `pointercancel`) 하나로 통일한다.
마우스·터치·펜이 같은 코드 경로를 타므로 분기와 중복 처리(터치 후 마우스
이벤트가 뒤따라 발생하는 문제)가 사라진다. 지원 범위도 충분하다.

흐름:

1. **`pointerdown`** (격자 컨테이너에서 위임 처리) — `isDrawing = true`,
   포인터 아래 칸을 즉시 칠한다. 클릭 한 번으로 도트 하나가 찍히는 경로다.
2. **`pointermove`** — `isDrawing`일 때만 포인터 아래 칸을 칠한다.
   드래그로 이어 그리기.
3. **`pointerup` / `pointercancel`** — `window`에 리스너를 걸어
   `isDrawing = false`. 격자 밖에서 버튼을 떼도 상태가 남지 않게 한다.

### 포인터 아래 칸을 찾는 방법

터치에서는 브라우저가 `pointerdown` 대상 요소로 **암시적 포인터 캡처**를
걸기 때문에, 손가락을 옮겨도 `pointermove`의 `event.target`이 처음 누른 칸에
고정된다. 마우스처럼 `event.target`만 믿으면 터치 드래그가 동작하지 않는다.

해결책으로 두 가지가 있다.

- (A) `pointerdown`에서 `releasePointerCapture()`를 호출해 캡처를 풀고
  `event.target`을 그대로 쓴다.
- (B) 매번 `document.elementFromPoint(e.clientX, e.clientY)`로 좌표 아래
  요소를 직접 찾는다.

**(B)를 택한다.** 마우스와 터치가 완전히 같은 한 줄을 타서 분기가 없고,
캡처 해제에 따르는 브라우저별 미묘한 차이에 기대지 않는다. 찾은 요소에
`dataset.index`가 없으면(격자 밖) 아무 것도 하지 않는다. 16×16 규모에서
`elementFromPoint` 호출 비용은 문제되지 않는다.

### 터치 중 페이지 스크롤 차단

- 격자 컨테이너에만 **`touch-action: none`**을 준다. 이것이 1차 방어선이며,
  브라우저가 스크롤·핀치 줌 제스처를 시작하기 전에 차단해 `pointercancel`로
  선이 끊기는 현상을 막는다.
- `body`나 문서 전체에는 걸지 않는다. 격자 밖에서는 페이지가 정상적으로
  스크롤되고 핀치 줌도 가능해야 한다(확대 접근성 존중).
- 추가로 `pointerdown` 핸들러에서 `event.preventDefault()`를 호출해
  텍스트 선택과 드래그 고스트를 막는다. 칸에는 `user-select: none`도 함께 준다.
- `viewport` 메타 태그에서 `user-scalable=no`는 쓰지 않는다.

### 칠하기 규칙

- 이미 같은 색이 칠해진 칸을 다시 눌러도 **토글하지 않고 그냥 덮어쓴다.**
  드래그 중 토글은 지나간 칸이 켜졌다 꺼졌다 하며 결과를 예측할 수 없게 만든다.
  지우기는 지우개 도구로만 한다 — 동작이 하나의 의미만 갖게 하는 쪽을 택했다.
- 성능/불필요한 DOM 쓰기를 막기 위해, 칠하려는 값이 현재 값과 같으면
  `pixels[]`와 DOM을 건드리지 않고 반환한다.
- 렌더링은 **부분 갱신**이다. 바뀐 칸의 `style.backgroundColor`와
  `aria-label`만 갱신한다. 전체 재렌더 함수는 "모두 지우기"에서만 쓴다.

### 지우개

- 팔레트 색이 아니라 **별도의 도구 버튼**으로 둔다. 팔레트 안에 "투명 스와치"로
  섞어 넣으면 색 선택과 도구 선택이 한 축에 뒤섞여 현재 상태를 읽기 어려워진다.
- 선택하면 `currentColor = null`이 되고, 칠하기는 해당 칸을 `null`로 되돌린다.
  화면에서는 체커보드가 다시 드러난다.
- 버튼은 `aria-pressed`로 눌림 상태를 노출한다. 지우개를 켜면 팔레트의
  선택 표시는 해제된다(선택 색은 기억해 두었다가 다시 색을 고를 때 복원하지
  않는다 — 사용자가 명시적으로 색을 다시 누르게 한다. 상태 하나를 줄이는 쪽).
- **모두 지우기** 버튼도 도구줄에 둔다. 되돌리기가 없으므로 실수로 전체를
  날리지 않도록 `confirm()`으로 한 번 확인한다.

## 색상 팔레트

### 16색 고정 팔레트 + 커스텀 색상 1칸

색 수는 **16색**으로 정한다. 격자와 같은 수라 기억하기 쉽고, 4×4 또는 8×2로
배치하면 모바일 세로 화면에서도 한 화면에 들어온다. 고전 픽셀 아트 팔레트
(EGA, PICO-8 계열)가 대체로 16색 안팎이라는 관례와도 맞고, 그 이상은
스와치가 작아져 44×44px 터치 타깃을 지키기 어려워진다.

색 선정 기준: (a) 무채색 4단계로 명암을 만들 수 있을 것, (b) 색상환을 고르게
덮을 것, (c) 라이트/다크 배경 어디에 올려도 스와치가 배경에 묻히지 않을 것.

| # | 이름 | 값 | 비고 |
|---|---|---|---|
| 1 | 먹색 | `#1b1b1b` | 순수 검정 대신. 다크 배경에서도 형태가 보인다 |
| 2 | 진회색 | `#545454` | |
| 3 | 회색 | `#9a9a9a` | |
| 4 | 흰색 | `#ffffff` | 그림 데이터이므로 순수 흰색을 허용한다(본문 텍스트가 아님) |
| 5 | 갈색 | `#7f4f24` | 나무·흙·피부 그림자 |
| 6 | 빨강 | `#e03131` | |
| 7 | 주황 | `#f76707` | |
| 8 | 노랑 | `#f2c94c` | |
| 9 | 연두 | `#74b816` | |
| 10 | 초록 | `#2f9e44` | |

**중요: 이 16색은 UI 색이 아니라 그림 데이터다. 다크모드에서 재정의하지
않는다.** 다크모드에서 색이 바뀌면 같은 그림이 테마에 따라 다르게 보이고
저장 결과와도 어긋난다. 팔레트 색은 `script.js` 안의 상수 배열에 두고,
CSS 토큰 체계(`:root`)에는 넣지 않는다. 토큰으로 관리하는 것은 스와치를
감싸는 테두리·선택 링·배경 같은 **UI 색**뿐이다.

### 커스텀 색상 — 포함한다

`<input type="color">`를 팔레트 끝에 한 칸으로 넣는다. 판단 근거:

- 브라우저 기본 위젯이라 **추가 코드도 외부 의존성도 0**이다. HSV 피커를
  직접 만들면 그것만으로 이 앱에서 가장 복잡한 코드가 된다.
- 모바일에서도 OS 기본 색 선택기가 뜬다.
- 16색만으로는 중간 톤(그림자·하이라이트)을 만들 수 없어, 픽셀 아트에서
  가장 아쉬운 지점을 정확히 메운다.
- 위험 요소는 스타일링이 브라우저마다 조금씩 다르다는 것뿐인데, 다른
  스와치와 같은 크기의 정사각형으로 감싸면 충분히 흡수된다.

`input`의 `change` 이벤트에서 `currentColor`를 그 값으로 바꾸고, 해당 칸이
선택 상태가 된다. 마지막으로 고른 커스텀 색은 그 칸의 배경색으로 남아
다시 누르면 재사용할 수 있다.

### 팔레트 UI 구조와 선택 상태

- 마크업: `<div role="radiogroup" aria-label="색상 팔레트">` 안에
  각 색을 `<button role="radio" aria-checked="true|false">`로 둔다.
  라디오 그룹은 "여럿 중 하나만 선택"이라는 의미를 정확히 표현하고,
  스크린리더가 "빨강, 라디오 버튼, 선택됨, 16개 중 6번째"처럼 읽어 준다.
  스와치 안에는 텍스트가 없으므로 `aria-label`에 색 이름을 넣는다.
- 선택 표시는 **색에만 의존하지 않는다.** 선택된 스와치는 (a) 굵은 외곽
  링(`box-shadow`로 배경색 링 + 강조색 링 이중), (b) 체크 표시(순수 CSS로
  그린 ✓ 또는 안쪽 사각형)를 함께 준다. 색맹 사용자와 저대비 환경 모두를
  고려한 결정이다.
- 스와치 크기는 최소 44×44px. 팔레트는 `display: grid`,
  `grid-template-columns: repeat(auto-fit, minmax(2.75rem, 1fr))`로 화면 폭에
  따라 8×2 ↔ 4×4로 자연스럽게 접히게 한다.
- 키보드: 라디오 그룹 패턴에 맞춰 **로빙 tabindex**를 쓴다. 그룹 전체가 탭
  정지 1개이고, 방향키로 스와치 사이를 이동하며 이동 즉시 선택된다
  (`Home`/`End`는 처음/끝). Tab을 16번 눌러야 격자에 도달하는 상황을 막는다.
- 현재 선택 색은 화면에도 텍스트로 표시한다("선택: 빨강"). 동시에 이 영역을
  `role="status" aria-live="polite"`로 두어 색을 바꿀 때 스크린리더가
  알리게 한다. 시각적 표시와 보조기술 안내를 한 요소로 처리하는 방식이다.

## PNG 저장

### 저장 크기 — 16×16 원본이 아니라 ×16 확대한 256×256

- 16×16 PNG는 실제로 쓰기 어렵다. 파일 탐색기·SNS·메신저 미리보기에서
  점 하나로 보이고, 대부분의 뷰어가 확대할 때 부드럽게 보간해 픽셀 아트의
  형태를 뭉갠다.
- **정수배(×16) 확대에 스무딩을 끄면 정보 손실이 0이다.** 16픽셀마다 정확히
  같은 값이 반복되므로 원본 16×16을 언제든 되복원할 수 있다. 즉 확대 저장은
  손해 없이 사용성만 얻는 선택이다.
- 256×256 PNG는 도트 그림 특성상 파일 크기도 수 KB 수준이다.
- 원본 크기 저장 옵션은 넣지 않는다. 버튼 하나가 늘면 "둘 중 뭘 눌러야 하지"라는
  판단을 사용자에게 떠넘기게 되고, 위 근거대로 확대본이 상위 호환이다.

### 흐름

```
saveAsPng():
  1. document.createElement('canvas')  // DOM에 붙이지 않는 오프스크린
  2. src = 16×16 캔버스 — pixels[] 를 순회하며 null이 아닌 칸만
     ctx.fillRect(col, row, 1, 1)   (null 칸은 그리지 않음 → 투명 유지)
  3. out = 256×256 캔버스
     out.ctx.imageSmoothingEnabled = false
     out.ctx.drawImage(src, 0, 0, 256, 256)
  4. url = out.toDataURL('image/png')
  5. <a href=url download=filename> 를 만들어 click() 후 제거
```

- **화면용 캔버스와 저장용 캔버스를 분리한다** — 정확히 말하면 화면에는
  캔버스가 아예 없다(DOM 격자). 저장용 캔버스는 버튼을 누른 순간에만
  만들어져 쓰이고 버려진다. 상시 유지되는 캔버스가 없으므로 화면 상태와
  저장 결과가 어긋날 여지가 구조적으로 없다. 두 캔버스를 쓰는 이유는
  `drawImage` 확대에 스무딩 끄기를 적용하기 위해서다(16×16에 직접
  `fillRect(col*16, row*16, 16, 16)`으로 그려도 되지만, 원본/확대 단계가
  분리돼 있으면 배율 상수 하나만 바꾸면 되고 반올림 오차가 없다).
- `toBlob()` + `URL.createObjectURL()`이 메모리 면에서 더 낫지만, 256×256
  PNG는 data URL로도 수십 KB라 문제가 없고 `toDataURL()` 쪽이 동기 코드로
  단순하다. **`toDataURL()`을 쓴다.**

### 투명 배경

- 지우개로 비운 칸(`pixels[i] === null`)은 캔버스에 아무 것도 그리지 않으므로
  **알파 0으로 저장된다.** 캔버스를 흰색으로 미리 채우지 않는다.
- 배경을 흰색으로 저장하고 싶은 사용자는 흰색(#ffffff)으로 칠하면 된다.
  "배경 투명/흰색" 옵션 토글은 넣지 않는다(비범위).
- 화면의 체커보드는 CSS 장식일 뿐 데이터가 아니므로 저장 결과에 나타나지 않는다.

### 파일명

`pixel-art-YYYYMMDD-HHMMSS.png` (예: `pixel-art-20260909-142530.png`).
로컬 시각 기준. 여러 장을 연달아 저장해도 브라우저가 `(1)`을 붙이지 않고
파일이 구분되며, 정렬하면 시간순이 된다.

저장 직후 `role="status"` 영역에 "PNG로 저장했습니다"를 표시한다 —
다운로드가 조용히 끝나는 브라우저에서 성공 여부를 알 수 있게 한다.

## UI/디자인

### 레이아웃

모바일 우선 세로 스택 → `min-width` 미디어 쿼리로 넓힌다.

- **모바일(기본)**: 헤더(제목 + 테마 토글) → 격자 → 도구줄(지우개 / 모두
  지우기 / PNG 저장) → 팔레트 → 현재 선택 표시 → 조작 안내.
  격자를 팔레트보다 위에 두는 이유는 그리는 동안 시선이 격자에 머물고,
  팔레트는 색을 바꿀 때만 내려다보면 되기 때문이다.
- **넓은 화면(`min-width: 48rem`)**: 2열 — 왼쪽에 격자, 오른쪽에 도구줄 +
  팔레트 + 안내. 격자는 `max-width: 30rem`을 넘지 않는다.
- 모든 크기는 `max-width`, `rem`, `clamp()`, `%`로 잡는다. 고정 px 폭은 없다.
- 본문 컨테이너는 `max-width: 60rem; margin-inline: auto; padding-inline: 1rem`.

### 색 토큰

`:root`에 정의하고 규칙 안에서는 하드코딩된 색을 쓰지 않는다.

```css
:root {
  --bg: #fdfdfc;
  --bg-subtle: #f4f4f2;
  --text: #1a1a18;
  --text-muted: #6b6b66;
  --border: #e4e4e0;
  --accent: #2f6f4e;        /* 선택 링, 포커스 링 */
  --grid-line: #d8d8d4;     /* 격자선 */
  --checker-a: #ffffff;     /* 빈 칸 체커보드 밝은 쪽 */
  --checker-b: #eeeeea;     /* 빈 칸 체커보드 어두운 쪽 */
  --swatch-ring: #fdfdfc;   /* 선택 스와치 안쪽 링(배경색과 같은 톤) */
}
```

블로그 `src/assets/style.css`의 토큰 이름·값을 그대로 따와 시각적 연속성을
유지하되, **파일을 import하지 않고 `apps/pixel-art/style.css` 안에 독립적으로
정의한다** (앱은 블로그와 별도로 열릴 수 있어야 한다).

### 다크모드

토큰 이름을 그대로 두고 값만 재정의한다. 다크 전용 셀렉터를 새로 만들지 않는다.

```css
:root[data-theme="dark"] { --bg: #161614; /* … */ }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { --bg: #161614; /* … */ }
}
```

- 다크 값에서 본문 텍스트는 순수 흰색이 아닌 `#e8e8e4` 계열, 배경은 순수
  검정이 아닌 `#161614`를 쓴다. 본문 대비 4.5:1 이상을 유지한다.
- 체커보드는 다크에서 `--checker-a: #232320` / `--checker-b: #1c1c1a`처럼
  어두운 두 톤으로 재정의한다. 밝은 체커보드를 다크 화면에 그대로 두면
  빈 칸이 눈부시게 튄다.
- **팔레트 16색은 재정의 대상이 아니다**(위 팔레트 절 참고).
- 상태 3가지(라이트 / 다크 / 시스템 따름)를 `<button aria-label="…">` 토글로
  순환시키고 `localStorage`(`pixel-art-theme`)에 저장한다. FOUC 방지를 위해
  `<head>` 인라인 `<script>`에서 CSS 로드 전에 `data-theme`를 지정한다.
  이 스크립트만은 외부 파일로 분리하지 않는다.

### 애니메이션

- 거의 쓰지 않는다. 칸을 칠할 때 트랜지션을 주면 빠른 드래그에서 색이
  뒤늦게 따라오며 어디까지 칠했는지 알기 어려워진다. **칸 색 변화는 즉시**다.
- 트랜지션은 스와치 선택 링과 버튼 hover/focus에만, 120ms 이내로 준다.
- `@media (prefers-reduced-motion: reduce)`에서 모든 트랜지션·애니메이션을
  `none`으로 끈다.

## 접근성/반응형

### 키보드만으로 그릴 수 있는가 — 가능하다

DOM 격자를 택했기 때문에 별도의 대체 UI 없이 구현할 수 있다.

- 격자는 `role="grid"`, 각 행은 `role="row"`, 각 칸은
  `<button role="gridcell">`이다. 칸에 `role="gridcell"`을 주는 것은 "버튼"보다
  **격자 안 위치**가 이 앱에서 더 중요한 정보이기 때문이다(스크린리더가
  `aria-rowindex`/`aria-colindex`로 좌표를 읽어 준다). 활성화 키 처리는
  어차피 직접 하므로 버튼 역할을 잃어도 손해가 없다.
- **로빙 tabindex**: 격자 전체가 탭 정지 1개. 포커스된 칸만 `tabindex="0"`,
  나머지는 `-1`.
- 키 매핑:
  - 방향키 — 칸 이동(격자 경계에서 멈춤)
  - `Enter` / `Space` — 현재 칸을 선택 색으로 칠하기
  - `Backspace` / `Delete` — 현재 칸 지우기(도구를 바꾸지 않아도 됨)
  - `Home` / `End` — 행의 처음 / 끝, `Ctrl` 조합 시 격자 처음 / 끝
  - 방향키를 `Shift`와 함께 — 이동하면서 연속으로 칠하기(키보드판 드래그)
- 각 칸의 `aria-label`은 `"3행 5열, 빨강"` / `"3행 5열, 빈 칸"` 형태로,
  색이 바뀔 때 함께 갱신한다. 색 이름은 팔레트 상수의 이름을 쓰고,
  커스텀 색은 `"3행 5열, 사용자 색 #a1b2c3"`으로 표기한다.
- 방향키 이동 시 페이지가 스크롤되지 않도록 `preventDefault()`를 호출한다.

### 반응형

- 뷰포트 375px에서 격자·팔레트·도구줄이 모두 화면 폭 안에 들어오고
  `body`에 가로 스크롤이 생기지 않아야 한다. 격자는 `width: min(100%, 30rem)`
  이라 자동으로 줄어들고, 팔레트는 `auto-fit`으로 줄바꿈된다.
- 도구줄 버튼은 텍스트 레이블을 유지한다(아이콘 폰트를 쓸 수 없고, 유니코드
  기호만으로는 의미가 불분명하다). 좁은 화면에서는 `flex-wrap: wrap`으로
  두 줄이 되게 한다.
- 터치 타깃: 도구 버튼·테마 토글·팔레트 스와치 모두 최소 44×44px.
  격자 칸은 375px에서 약 21px로 44px에 못 미치지만, 이는 16×16 격자를
  한 화면에 담는다는 요구사항에서 불가피하다. 대신 (a) 격자를 화면 폭
  전체로 키워 칸을 최대한 크게 만들고, (b) 핀치 줌을 막지 않아 사용자가
  확대해서 정밀하게 찍을 수 있게 한다. 이 예외를 문서에 남긴다.
- `viewport` 메타에 `user-scalable=no`, `maximum-scale`을 쓰지 않는다.

### 그 외

- 시맨틱 태그: `<main>`, `<header>`, `<footer>`, 도구 묶음은 `<section>` +
  `aria-labelledby`.
- 본문 건너뛰기 링크는 페이지가 한 화면짜리 단일 앱이라 넣지 않는다.
  대신 격자가 탭 정지 1개라 팔레트·도구줄로의 이동이 이미 짧다.
- 포커스 링을 제거하지 않는다. 필요한 곳은 `:focus-visible`로 다시 디자인하되
  격자 칸에서는 링이 칸 밖으로 살짝 넘치도록(`outline-offset`) 해서
  칠해진 색을 가리지 않게 한다.
- JS가 꺼진 환경: 이 앱은 그리기 도구이므로 JS 없이는 기능하지 않는다.
  `<noscript>`로 "이 도구는 자바스크립트가 필요합니다"를 안내한다.
  (블로그 본문의 점진적 향상 원칙은 글 읽기에 대한 것이고, 앱 자체에는
  적용되지 않는다는 판단.)

## 외부 의존성

**없음.** CDN을 포함해 어떤 외부 요청도 만들지 않는다. 폰트는 시스템 폰트
스택(한글 가독성 우선), 아이콘은 텍스트 또는 순수 CSS로 대체한다.
색 선택은 브라우저 내장 `<input type="color">`, PNG 인코딩은 브라우저 내장
`canvas.toDataURL()`을 쓰므로 라이브러리가 필요한 지점이 없다.
`index.html`이 받는 파일은 자기 자신 + `style.css` + `script.js` 세 개뿐이다.

## 비범위 (out of scope)

- **되돌리기(undo) / 다시 실행(redo)** — 히스토리 스택과 그에 딸린 UI가
  이 앱에서 가장 큰 복잡도가 된다. 지우개와 `Backspace`로 국소 복구가
  가능하고, 16×16은 다시 그리는 비용도 작다는 판단.
- **레이어**
